STEP 4 - OPEN ITEM A: JHU PHANTOM ZEROS 2011-2014
================================================================================
The JHU baseline is READ-ONLY. It was not modified. Investigation only.

FINDING 1 - `Phantom` is not a column.
  grep -rn "Phantom" py/  ->  matches ONLY in py/convert_jhu_to_workflow.py.
  Line 148 reads Phantom from the JHU source; line 171 embeds it in free-text
  processing_notes; line 88-89 uses it to multiply confidence by 0.7 (which is
  why ETH JHU rows 228-231 carry 0.7 against 1.0 on the 2019-2021 rows).
  It is never emitted as a column, so py/build_weekly_timeseries.py cannot read
  it and never references it. Ethiopia has 11 Phantom:True JHU rows, of which
  four are the 2011-2014 zeros; the other seven carry positive counts.

FINDING 2 - a partial mitigation already exists.
  py/build_weekly_timeseries.py line ~424-428 grades a zero as documented_zero
  only when the row's own "Evidence type:" token says so; everything else,
  "incl. JHU annual zeros" per the code comment, becomes inferred_zero with
  confidence clamped to INFERRED_ZERO_MAX = 0.6. So these zeros are NOT
  masquerading as documented absence.

FINDING 3 - they still assert zero. Verified empirically.
  Imported build_weekly_timeseries and called process_country('ETH', ...) in
  memory with a uniform template (main() writes into all 40 country directories
  and the shared figure dir, so it was NOT run). Result:
    2011: 52 weeks, all {'JHU','inferred_zero'}, 0 positive weeks
    2012: 52 weeks, all {'JHU','inferred_zero'}, 0 positive weeks
    2013: 52 weeks, all {'JHU','inferred_zero'}, 0 positive weeks
    2014: 52 weeks, all {'JHU','inferred_zero'}, 0 positive weeks
  208 weeks of asserted zero. 2011 is contradicted by AI Index 555/556
  (13 and 3 AWD cases, Kebri Dahar) and 7 presence records; WHO GHO carries no
  Ethiopian cholera row at all for 2011-2014.

FINDING 4 - a separate, more general pipeline defect, verified by experiment.
  py/build_weekly_timeseries.py, process_country() -> try_insert(), line 374:
      if SOURCE_PRIORITY[entry["source"]] > SOURCE_PRIORITY[existing["source"]]:
          merged[key] = entry
  Source priority overrides unconditionally and ignores `method`. The
  method-rank tiebreak at line 378 applies only within one source. The guard at
  line 430 (`if src_label == "JHU" and key in weekly_covered`) is reset per
  source at line 396, so it protects only JHU's own weekly rows.
  SOURCE_PRIORITY = {"WHO":3, "JHU":2, "AI":1} (line 54).
  => a JHU/WHO inferred_zero at confidence 0.6 silently overwrites an AI
     `observed` positive at confidence 0.9.

  EXPERIMENT (monkeypatched load_national_rows, in memory, nothing written):
    injected a synthetic AI NATIONAL observation, week 2013-W23, sCh=500,
    deaths=5, confidence 0.9, evidence documented.
    Result for (2013, 23):
      {'sch': 0.0, 'deaths': 0.0, 'source': 'JHU', 'confidence': 0.6,
       'method': 'inferred_zero'}
    The AI observation vanished.

  Ethiopia is shielded only by accident: rows 555/556 are sub-national and
  load_national_rows() filters to Location == "AFR::ETH" exactly, so the
  contradicting evidence never reaches the national series. Any country with an
  AI national positive overlapping a JHU/WHO annual zero is exposed today.

  NO PIPELINE CODE CHANGED - this affects all 40 countries and is the owner's

Agent 6 annotated rather than retracted. CONFIRMED CORRECT.
  The row quotes WER No. 35 exactly ("as of 26 July 2026 ... 1 January to
  26 July 2026 Cases 50, Deaths 2"). The count is real and the quote is faithful,
  so retracting would destroy true information.
  But WHO's own global cholera dataset on HDX records Ethiopia adm0
  last_epiwk = 2026-03-02, case_total 50 - the cumulative has not moved since
  March, and the WER date is the publication's data-as-of date.
  Consequence quantified: the analyser credits TL..TR as covered, so the recent
  gap reports as 2026-08-01..2026-09-20 (51 days) when the true non-reporting
  tail starts 2026-03-03 and runs ~6.5 months. All four of Ethiopia's AI-only
  months (2026-04..2026-07) are credited by this single row.
  The fault is in how cumulative "as-of" rows are credited, not in the row.
  Logged as recommendation R6. Do not write a zero for this window.
