FACT 1.  The validator's "row N" is the PHYSICAL CSV LINE NUMBER, not the Index
column (py/validate_quality.py line 213: r["_line"] = rdr.reader.line_num; line
598 prints prev_line).  Every conflict pair in the orchestrator's docket item B
was quoted by line number.  The docket's "rows 76/45, 78/46 ..." are lines, and
for the later pairs line and Index diverge sharply: docket "110/26" is Index
153 vs Index 26; "197/16" is Index 240 vs Index 16; "1022/44" is Index 1085 vs
Index 44.  Acting on those numbers as Indices would have revised eight wrong
rows.  Mapping table is given in the register below.

FACT 2 - AND THIS IS THE FINDING THAT MATTERS MOST THIS PASS.
py/build_weekly_timeseries.py try_insert() (lines 369-387) resolves two rows
covering the same week as follows: higher SOURCE_PRIORITY wins; on a tie it
prefers the better method rank; and on a tie there it prefers THE HIGHER sCh.
Every AI row carries the same source label, so for two AI rows describing the
same week the builder silently keeps WHICHEVER REPORTS MORE CASES.

Consequence: DOWNWEIGHTING A ROW THAT IS KNOWN TO BE WRONG DOES NOT PROTECT THE
SERIES.  confidence_weight is not consulted by try_insert at all.  A row that
has been falsified by a primary source but left in the file at confidence 0.2
still overwrites the correct smaller value.  Seven such rows were found in this
file (the 2023 state block, item B) - each already carefully annotated
"SUPERSEDED AND NON-PRIMARY" by a previous agent and each still winning.
Annotation was the right instinct and the wrong instrument.  Where a value is
demonstrably falsified rather than merely disputed, the correct action is
RETRACTION (which writes a tombstone, so nothing is lost) or CORRECTION, not
downweighting.  That rule governs my disposition of items A and B below.
